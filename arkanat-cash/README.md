# بوابة العهد النقدية — أركانات

نسخة MVP مستقلة تعمل من المتصفح ولا ترتبط حالياً بـ Guard Control أو أي نظام مؤسسي آخر.

## الإصدار الحالي
v1.2 — بوابة مشتركة مستقلة منطقياً مع Super Admin، إدارة المستخدمين، حسابات عهد مستقلة حسب النوع، ربط المستندات المؤيدة، ومنع تكرار متعدد الطبقات.
- وضع Delta للملفات التي تحتوي حركات إضافية فقط، مع تجاوز المكرر.
- إيقاف أي شيت غير معروف بدلاً من استيراده بتفسير خاطئ.\n- تعيين يدوي لصف العناوين ونوع الملف والأعمدة عند ظهور صيغة Excel مستقبلية غير معروفة، بدون تعديل الملف الأصلي.

## فلسفة البيانات
- فصل حامل العهدة عن المشرف التشغيلي عند اختلافهما.
- العهد الفرعية المفتوحة تبقى نقداً بعهدة الشركة وليست مصروفاً.
العملية النقدية هي الوحدة الأساسية، وليس ملف الشهر. ملف Excel يعد مصدراً أو Snapshot يمكن استيراده، بينما تحتفظ البوابة بتاريخ المصدر والحركة وحالتها لتجنب ازدواج الاحتساب.

## المرحلة الحالية
النسخة تجريبية وتخزن البيانات محلياً. الهدف الحالي تثبيت دورة العمل واختبار الاستيراد والتصدير قبل الانتقال إلى قاعدة بيانات مشتركة متعددة المستخدمين.


## التحقق
تم اختبار المحرك مقابل ملفات فعلية من الشرقية والرياض والغربية ودفاتر المشرفين وطلبات العهد وملفات الوقود التاريخية. التفاصيل في `UAT_RESULTS.md`.


## دورة العمل اليومية للمالية
1. تسجيل طلب العهدة كما ورد من المشرف، مع قناة الطلب والنص الأصلي عند الحاجة.
2. مراجعة الطلب واعتماده أو طلب استكماله أو رفضه.
3. الاعتماد لا ينشئ حركة نقدية.
4. عند تنفيذ الصرف تسجل المالية عملية التمويل مستقلة، ويمكن أن يكون التمويل جزئياً أو كاملاً.
5. كل تنفيذ تمويل ينشئ حركة تغذية مرتبطة برقم الطلب ووسيلة الدفع ومرجع التنفيذ.
6. التغطيات والمصروفات تسجل أو تستورد إلى دفتر الحركة.
7. نهاية الفترة تستخدم شاشة التصفية وملخص المواقع ومرشحات الاسترداد للمراجعة.
8. جميع الإجراءات المهمة تحفظ في سجل التدقيق مع اسم مستخدم الجهاز.

## مبدأ مهم
الرسالة أو الطلب هو مصدر العملية، لكنه ليس القيد المالي نفسه. لذلك يحتفظ النظام بنص الطلب/البلاغ وقناة وروده، ثم تفصل المالية بين الاعتماد والتنفيذ والتسجيل.


## البنية المشتركة الحالية
- الاستضافة: GitHub Pages.
- قاعدة البيانات: جداول مستقلة باسم `cash_*` داخل مشروع Supabase قائم في اشتراك Arkanat Org الحالي.
- لا توجد مفاتيح أجنبية أو روابط إلى جداول Guard ERP أو Guard Control.
- الوصول محصور بالمستخدمين الموجودين في `cash_portal_access`.
- RLS مفعّل على جميع جداول البوابة.
- لا يوجد وصول Anonymous إلى بيانات العهد.
- لم يتم إنشاء مشروع Supabase جديد، وبالتالي لا توجد تكلفة Compute إضافية ناتجة عن هذه البوابة.
- ملفات Excel الأصلية لا ترفع إلى GitHub؛ تحليلها يتم في المتصفح ثم تحفظ السجلات المنظمة فقط.


## إدارة المستخدمين
- الحساب `ttt0600@hotmail.com` هو **Super Admin** الوحيد حالياً.
- Super Admin يستطيع إنشاء مستخدم جديد من داخل البوابة بإدخال الاسم والبريد والدور وكلمة المرور الأولية.
- الأدوار المتاحة: مدير مالية، موظف مالية، قارئ فقط.
- لا يمكن إنشاء Super Admin آخر من واجهة البوابة.
- كلمات المرور لا تحفظ في جداول البوابة أو سجل التدقيق.
- يمكن لـ Super Admin إعادة تعيين كلمة مرور الحسابات التي أُنشئت من بوابة العهد.
- إذا كان البريد موجوداً مسبقاً في مشروع Supabase، تمنح له صلاحية البوابة بدون تغيير كلمة مروره حتى لا يتأثر استخدامه في أي خدمة أخرى داخل المشروع.
- تعطيل المستخدم يمنع دخوله إلى بوابة العهد فقط ولا يحذف حساب Auth.


## حسابات العهد والمستندات المؤيدة
- حساب العهدة أصبح يتحدد بمفتاح: المنطقة + حامل العهدة + نوع العهدة.
- عهدة التغطيات منفصلة عن عهدة الوقود لنفس المشرف.
- المصروفات المرحلة من حساب شخصي في عهدة سابقة تعامل كرصيد افتتاحي سالب وليست مصروف فترة جديد.
- المستندات المؤيدة تحفظ في cash_transaction_evidence وتربط مباشرة بالحركة النقدية.
- ملف فواتير راشد (7 صفحات) رُبط بحركات وقود بروق السبع بقيمة إجمالية 697 ريال مع مطابقة التاريخ والمبلغ ورقم الفاتورة/المرجع.
- أي مصروف تشغيلي بلا رقم فاتورة أو مستند مؤيد يبقى في قائمة المراجعة.

## منع التكرار في الاستيراد
- مستوى 1: بصمة SHA-256 للملف بالكامل.
- مستوى 2: بصمة الحركة/الطلب باستخدام التاريخ والمبلغ والحساب والبيانات التشغيلية.
- مستوى 3: كشف التعارض عند تطابق هوية العملية مع اختلاف القيمة.
- الملف المطابق بالكامل لا يعاد استيراده إلا بتجاوز Super Admin مع تسجيل السبب في سجل التدقيق.
- Snapshot يحيّد اللقطة السابقة لنفس الحساب والفترة بعد اكتمال الاستيراد، ولا يحذفها.
